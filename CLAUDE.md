# patch-press

Automatically captures VST presets or loads sample libraries and exports ready-to-play presets for hardware samplers — Deluge (XML + WAV), Polyend Tracker (self-contained `.pti`) or 1010music Bento (a `patch.xml` folder per preset). Zero manual YAML writing is the goal — scan commands handle discovery, YAML files are the escape hatch when auto-detection gets something wrong.

## Pipeline

```
YAML config → load_config() → VSTAdapter or LibraryAdapter
                                        ↓
                              analyze_sampleset()
                              (trim, envelope, pitch*, loop, normalize)
                                        ↓
                        Exporter (--format deluge|pti|bento) → preset files
```

*Pitch verification runs only for library sources, never for VST.

## Commands

| Command | Purpose |
|---|---|
| `scan-from-probe <probe-dir> <config-dir>` | Analyse patch-probe YAMLs, write one config per preset |
| `scan-library <folder> <config-dir> --type multisample\|kit\|drumkit` | Write one YAML per subfolder of a sample library |
| `scan-oneshots <folder> <config-dir>` | Write one YAML per WAV in a folder of single-note oneshot presets (e.g. Monosounds) |
| `scan-wavetables <folder> <config-dir>` | Write one YAML per WAV in a folder of Serum-format wavetables (e.g. Liam Wavetables — note filenames may be uppercase `.WAV`, so every WAV glob in the scan/adapter path is `case_sensitive=False`) |
| `scan-bitwig <folder> <config-dir>` | Write one YAML per Bitwig `.multisample` archive (searched recursively; e.g. Orchestral Tools packs) |
| `assemble-kits <folder> <config-dir>` | Synthesize kit configs from a bag-of-hits library organized by instrument category (e.g. Samples From Mars "Individual Hits") |
| `sample <config.yaml>` | Run the full pipeline for one config |
| `batch <configs/*.yaml>` | Run all configs sequentially, skip existing outputs |

## Profiles

Four profiles exist: `synth` (melodic, full range), `pad` (sustained + evolving/rhythmic timbre, still loops), `pluck` (no sustain to loop — also auto-assigned when the non-loopable detector flags a continuously-evolving timbre), and `drums` (multi-velocity, multi-RR, no note_range/note_step). `synth`/`pad`/`pluck` are auto-detected from probe classification (`_sound_type_to_profile` in `runner/scan.py`); duration and loop settings are inferred by the scan command — profiles are just the baseline.

## Key conventions

- Source type drives behaviour: VST skips pitch verification, library keeps it
- `scan-from-probe` re-renders each preset at `--probe-note` (default 60) to classify sustain type; `--note-step` (default 3) sets the semitone step between captured notes and `--duration` (default 15.0 s) sets the sustain capture duration
- **A library WAV is a finished master — the pipeline's job is to not touch it.** Two scan-time settings decide that, both written into the generated YAML so they're visible and hand-editable. (1) `--loop-detect auto` (default) probes the scanned folder for `smpl` chunks: a library that ships them gets `analysis.loop_detect: false`, meaning loop points come *only* from the files — a WAV without a chunk is one its author left as a one-shot, and shipping it unlooped is respecting that, not losing a loop. Across SFM's 516 synth preset folders the split is all-or-nothing per folder (316 fully looped, 200 fully not, zero mixed), which is what makes the absence readable as intent. A library that ships no chunks at all keeps detection on — nobody expressed an intent, so detection is the only way it ever loops. This also kills the crossfade bake, the one genuinely destructive edit in the library path. (2) `--audio verbatim` (default for melodic; `processed` for kits) writes `trim: false` + `normalize: none`, because both are no-ops on a vendor master and either one forces a re-encode. Any sample that then reaches an exporter unmodified is copied byte-for-byte (`io/exporters/_common.py:write_sample_wav`) instead of re-encoded to 16-bit dual-mono — the flag is `metadata["audio_verbatim"]`, set by `LibraryAdapter` at read time and cleared by every stage that alters a frame (trim, crossfade bake, normalize gain), so "unmodified" is *measured*, not assumed. Kits keep `processed`: a pad is expected to hit full scale, and vendors don't level them there (median +15 dB needed across this corpus, vs +5 dB for SFM melodic). Not applicable to `.pti`, which embeds its own PCM.
- Library filenames: note+octave parsed anywhere in the stem (`Mini_Patch_A#0_0001.wav` → note A#0, RR 1); base files (no `_NNNN` suffix) ignored when numbered RRs exist for the same note
- `scan-library` assumes one subfolder = one preset (multisample notes, a kit's per-instrument dirs, or — with `--type drumkit` — a flat folder of loose one-shot drum hits, e.g. Samples From Mars "808 From Mars"/"909 From Mars" kit folders). When a folder instead holds many loose single-note oneshot WAVs that are each their own preset (no shared notes to group by), use `scan-oneshots` on that folder instead — it writes one config per file, with the root note auto-detected via pitch tracking (since e.g. Monosounds filenames carry a pitch class but no octave) and pinned into `source.note`
- `--type drumkit`: each WAV in the flat folder becomes one kit pad; the instrument is identified purely from filename keywords (`analysis/drumkit.py:classify_instrument` — BD/SD/CH/OH/Clap/Rim/Tom Low·Mid·Hi/Conga Low·Mid·Hi/Cowbell/Claves/Maracas/Cym/etc, unrecognized tokens fall to `other` rather than being dropped). Deluge kit XML has no explicit note attribute — pad order is purely `<soundSources>` document order — so pads are sorted into the canonical kick → snare → closed/open hat → clap/percussion → cymbals → toms (low→high) → congas (low→high) → other order, matching Synthstrom's own factory kits (TR-808/TR-909/R-100). A folder where every file lands in the same single category (e.g. a chromatic one-instrument folder) is flagged REVIEW rather than silently shipped as a real kit.
- `assemble-kits`: for libraries that ship as a *browsing bank* rather than pre-made kits — one subfolder per instrument category, each subdivided by a descriptive "flavor" taxonomy that repeats across categories (Clean/Color/Tape/Various, etc — confirmed against a real vendor-shipped kit that it's not a guessed convention, see `analysis/drumkit_assemble.py`). Generates one kit per shared flavor tag (a tag only counts if it spans ≥2 instrument families — `--min-categories`), picking one file per category from that flavor's subfolder, falling back to that category's `Various` pool and then to any file when the exact flavor isn't available for that pad (flagged REVIEW). The resolved file list is written into `source.files` in the YAML once at scan time — `sample`/`batch` just load that fixed list, so a wrong pick is a one-line hand-edit, not a re-scan. **Scope boundary**: this only fires when flavor tags live in shared subfolder names; libraries where descriptive words only appear inside flat filenames (no shared subfolder taxonomy) aren't handled — that would need real audio-feature coherence, not built here.
- `scan-bitwig`: a Bitwig `.multisample` is a ZIP of WAVs + a `multisample.xml` that authoritatively maps each WAV to a key/velocity zone and (for sustaining sounds) a loop — so there's no filename parsing, pitch tracking, loop detection or probe rendering (`io/adapters/bitwig.py`, `analysis/drumkit`-style metadata read). The loop flag is bimodal per file (Bitwig writes `mode="loop"` on every zone of a sustaining articulation, `mode="off"` on every zone of a staccato/one-shot one), so profile follows it: all-loop → `synth` (ships authored loop), else → `pluck`. Root notes are ground truth (pitch_verify off). Per note the adapter keeps ONE velocity layer (nearest `source.velocity`, default 100 — hardware presets don't layer velocity and both exporters collapse anyway), thins by `note_step`, slices each WAV to its `[sample-start, sample-stop)` region (a looped note's region ends exactly at loop-end; Bitwig keeps unused recording past it), bakes the loop crossfade with Bitwig's own `fade` length and marks it authored so the pipeline ships it verbatim, and applies per-sample `gain`. Recursive scan; mirrors source subfolders into config tree + `output.subfolder`. Fixed-pitch-dominant files (`<key track="0">`, percussion maps) flagged REVIEW. See `docs/inputs/bitwig.md`.
- Wavetables (Serum-format, `clm` chunk, 2048 samples per cycle — a trailing partial window is dropped rather than rejected, since Polyend's own stock tables ship a few samples short and the Tracker floors to whole windows; stereo ships stereo to `.pti` as planar PCM with the length field counting frames per channel, and is downmixed only for the Deluge, whose wavetable oscillator is mono-only) are a different pipeline entirely — no trim/envelope/loop/normalize, the file ships to the SD card unmodified and its sound comes from the target device's own wavetable-scan oscillator (all three formats export them). `scan-wavetables` analyses each file's own spectral content (brightness, flatness, frame-to-frame timbral variance) to pick an archetype (pad/pluck/bass/lead/drone/evolving_pad) and WT-position/LFO2-depth — see `docs/inputs/wavetables.md` for the rationale and `analysis/wavetable.py` for the thresholds (first pass, tune by ear like the loop-detection constants elsewhere in this codebase)
- Output format is selected per-run via `--format deluge|pti|bento` (Deluge XML+WAV, self-contained Polyend Tracker `.pti`, or a 1010music Bento patch folder — see `docs/outputs/`); `output.name` in the config sets the preset name; the SD card / output directory is supplied via the CLI `--path` argument
- `--format bento` writes `UserPatches/SampInst|OneShots|Wavetable/<flat name>/patch.xml` with the WAVs alongside it (the patch references them by bare filename, so they must be siblings). Both the patch-type roots and the XML schema come from a real card's factory bank cross-checked against firmware strings, and generated patches are verified to match the factory attribute names and order. Three constraints shape the mapping: keyzones are explicit bottom/top so each sample's zone is **centred** on its root (half the repitch distance of the Deluge's upward-only ranges); a kit is exactly **16 pads**, so a bigger kit is thinned round-robin across instrument categories rather than truncated in canonical order (which would spend every slot on kicks and snares); and `loopmodes` is per-instrument, not per-sample, so a mixed set follows the majority with a warning. **Loop crossfade is NOT baked for bento** (unlike deluge/pti, which hard-wrap and need it in the audio): the device has `loopfadeamt` (front-panel `Loop Fade`), so the WAVs ship exactly as captured and the device fades the seam — a baked fade is permanent on the card, a parameter stays adjustable. `BentoExporter.bakes_loop_crossfade()` declares it (same optional-classmethod shape as `notes_used`); `runner/pipeline.py` passes `bake_crossfade=False` into `analyze_sampleset`, which still computes and records `analysis["loop_crossfade_ms"]` but leaves the audio alone. Authored loops (`loop_source == "authored_smpl"` — library `smpl` chunks, Bitwig zones) already loop cleanly, so they get `loopfadeamt=0`; only detected loops ask for the fade, and like `loopmodes` it's per-instrument so the majority decides. `_LOOP_FADE = 200` is a starting knob position, NOT derived — the firmware gives the parameter no units and the factory bank uses it in only 3 of 481 cells (100/200/299). Still baked: a Bitwig zone's own `fade`, applied in the adapter before any exporter is involved. Wavetables export too, to a third root — `UserPatches/Wavetable/<flat name>/patch.xml` (a `wttrack`), the table WAV beside it and named by the oscillator cell's `filename`. `wavesel` is a 0-based index into a 103-entry catalogue the firmware does carry (display names at `0x660f8`, filenames at `0x664f0`, matching `filename` in all 130 factory cells) but the firmware holds only the *names* — 103 tables at ~3 MB is ~300 MB against a 1.4 MB binary, and no wavetable library folder exists on the card, so every factory patch ships its own byte-identical copy of each table and `filename` is what selects the audio (`Double-tap to load WAV` / `No WAV` / `Invalid Wavetable` / `Wavetables must be mono WAVs.` are the firmware's load path). `wavesel` is written `0` — in range, so the picker shows *a* name rather than risking `Invalid Wavetable`. Mono is a hard firmware requirement, so a stereo table is downmixed (the one Bento sample that isn't shipped as captured). Cell order is the factory's invariant 14 (2×wavetable, osc, 2×filter, 2×env, 2×lfo, seqmod, partparms, 3×fx): both wavetable cells play the one table detuned ±6 cents with the position LFO inverted on the second (what 37 single-table factory patches do), the analog osc is silenced, env1 is the implicit amp envelope, and the analysis's `lfo2_*` lands on Bento LFO **1** (which is what drives `wavepos` in 93 factory cells vs LFO 2's 13).
- **Bento organisation is the folder name and nothing else.** No nesting (loader only resolves a `patch.xml` directly under the type root), no display-name field in `patch.xml`, and no user tags — the browser's filter row is a fixed 17-entry table in `bento1.bin` at `0x14e460` (`All`, 15 tag names, `User`), and every one of those tag strings is referenced exactly once, from that table. A hand-written *custom* tag is confirmed ignored on hardware, but the index file itself — `UserPatches/patchindex.xml`, `<patch path="UserPatches\SampInst\Name"><tag>Bass</tag></patch>`, backslashes, no BOM — **is honoured whether the device or a build wrote it** (user-confirmed on hardware), so `--format bento` writes it: `io/exporters/bento_index.py` derives up to 3 of the 15 legal tags per preset from the library's own folder labels (deepest subfolder → shallower → collection → preset name; a kit is `Drum` first; no signal at all → `Synth`), and upserts them under an `flock` (a `--jobs K` build has several `batch` processes claiming that one file), preserving entries the run didn't produce — including tags set on the device. Formatting is not load-bearing: the factory index indents its first entries with spaces and its last with tabs. Staging gotcha: `output/Bento/UserPatches/patchindex.xml` only knows this tree, so rsync it to a card with `--exclude patchindex.xml` or build straight to the card. So the one flat alphabetically-sorted name carries the whole hierarchy: `_flat_patch_folder` in `io/exporters/bento.py` shortens each level to a stable label (`Samples from Mars/Vinyl Synths from Mars/02. Keys & Pads/Polaris Space Delay Soft Vinyl Synths D2` → `SFM VS Keys Pads - Polaris Space Delay Soft D2`, median 57→31 chars over the ~2200-preset corpus). The prefix is a **pure function of collection + `output.subfolder`, never of the preset name**, and each label is shortened on its own length alone — anything name- or total-length-dependent scatters one bank across the flat list, which is the whole failure being fixed. Shortening can collide where a full path couldn't, so `run_batch` pre-checks the whole set and warns. See `docs/outputs/bento.md`
- Capture size is format-aware, and only there: an exporter declares which of a melodic note grid it actually ships (`notes_used(notes)` — Deluge keyzones every note, `.pti` has no keyzones and ships one repitched sample), and `runner/pipeline.py:notes_to_capture` consults it before a VST/CLAP render so a pti run doesn't pay for renders the export discards. Same method picks the sample at export time, so narrowed capture and export can't drift. Optional — an exporter without it gets the full grid. Nothing is cached between runs, so building both targets from one config renders twice
